# SpecGuard Architecture (v0)

## Objective

Provide a minimal, real foundation for PR-time spec drift tooling without over-engineering.

## Non-goals for v0

- No hosted services.
- No GitHub App/webhook backend.
- No advanced semantic analysis.
- No ML classifiers.

## v0 components

- `specguard.cli`
  - User-facing commands (`validate-config`, `scan-specs`, `check-pr`).
- `specguard.config`
  - JSON config loading and schema-lite validation.
- `specguard.changes`
  - Snapshot/directory diff for deterministic changed-file detection.
- `specguard.classify`
  - Heuristic file classification (`spec_docs`, `code`, `test`, `api_contract`).
- `specguard.rules`
  - Rule evaluation logic for behavior/spec/test alignment.
- `specguard.pr_check`
  - Orchestration layer returning text/json-friendly report payloads.

## Data flow (today)

1. User runs `specguard check-pr --config ... --base ... --head ...`.
2. Base/head snapshots are compared by relative path + file content hash.
3. Changed files are classified using path/filename heuristics.
4. Rule `behavior-code-requires-spec-and-tests` is evaluated:
   - if code changes exist, require both spec/docs evidence and test evidence,
   - unless a config waiver matches all changed code paths.
5. CLI renders either text summary or JSON report.

## What the v0 rule guarantees

- Deterministic pass/fail/waived result from explicit heuristics.
- Transparent evidence accounting (which files were considered code/spec/test).
- Machine-readable output suitable for future CI integration.

## What the v0 rule does not guarantee

- It does not prove true behavioral impact.
- It does not verify quality/completeness of tests.
- It does not semantically validate that docs truly describe code changes.
- It does not inspect GitHub PR metadata or issue links yet.

## Why Python CLI first

- Fast OSS iteration.
- Easy CI integration via GitHub Actions.
- Straightforward path to add git diff + PR metadata checks later.

## Incremental future scope

### Near-term (v1-ish)

- Add PR metadata evidence adapters (issue/spec references).
- Add machine-readable formats for annotations (e.g., SARIF/check summaries).
- Expand tests for edge-case rule scenarios and waiver policy controls.

### Mid-term

- GitHub Action wrapper.
- Rule adapters for:
  - GitHub Issues links,
  - ADR/RFC conventions,
  - OpenAPI contract deltas,
  - test evidence heuristics.

### Long-term

- Optional plugin interface for organization-specific policy checks.
- Rich PR annotations/check summaries.

## Assumptions

- Repos already keep some specs in Markdown/YAML/JSON form.
- Teams value deterministic, explainable checks before any AI assistance.
- Small-team maintainability is a hard requirement.
